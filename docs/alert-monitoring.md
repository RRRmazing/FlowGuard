# 预警监测：实现与阶段验收

本功能从与远端同步的 main `2bfd8dd` 创建 `feat/alert-monitoring`，在原项目目录开发。新增侧边导航“预警监测”，沿用 Qt 配色、告警表格和下方详情；规则设置按需展开。现有统计图表未增加内容。

## 检测规则

所有数量阈值均为“达到或超过”，窗口采用 `(t－窗口长度, t]`，窗口长度可设为 1—60 秒。默认值为起步示例，不能作为适用于所有网络的安全标准。

| 规则 | 分组与条件 | 默认窗口 / 阈值 |
| --- | --- | --- |
| 疑似 SYN 泛洪 | 按目的 IP＋目的端口统计初始 SYN；排除 ACK、FIN、RST 置位的报文 | 5 秒 / 500 包 |
| 回声请求频率异常 | 按目的 IP 统计 IPv4 ICMP Type 8 Code 0、IPv6 ICMPv6 Type 128 Code 0；不统计回声应答 | 5 秒 / 300 包 |
| 疑似 TCP 端口扫描 | 按来源 IP＋目的 IP，统计初始 SYN 尝试的不同目的端口；同端口重传不增加端口种类数 | 10 秒 / 20 个不同端口 |
| UDP 高频流量 | 按目的 IP＋目的端口统计 UDP 包数 | 5 秒 / 1000 包 |
| ARP 地址映射变化/冲突 | 对合法 Ethernet/IPv4 ARP 请求和应答记录发送方 IP→ARP 载荷内发送方 MAC；首次建立基线不报警，映射变化累计计数 | 60 秒 / 1 次变化 |

ARP 基线 300 秒无更新后过期，忽略 0.0.0.0 探测源、全零及广播 MAC。ARP 数据使用载荷内地址，不使用 Ethernet 头地址代替。规则只采用完整解析的报文，截断、错误或不支持的报文不作为有效证据。

## 输入、规则修改与结果

- 报文解析后直接送入后台 AlertMonitor，不经过界面最近 2000 条缓存，也不受显示筛选影响；采集 BPF 仍然限制实际可见范围。
- 实时采集和 PCAP 共用同一引擎，以报文捕获时间推进窗口，回放倍速不改变结论。实时空闲时按当前时间推进并判断恢复；停止或文件结束不伪造后续流量恢复。
- 同规则、同对象合并成一条，保留首次/最近触发时间、峰值、当前窗口数和关联报文序号。再次触发更新该条。人工“已确认”与检测“已恢复”分别表示查看状态和检测结果。
- 用户可随时修改开关、窗口、阈值，点击“应用规则”。实时模式只重算受影响规则的当前窗口，撤下不再符合标准的结果；其他规则保留。后台保留至多 360 秒、100000 条精简记录，以支持 300 秒 ARP 基线与最长 60 秒检测窗口。
- PCAP 模式异步从头扫描已处理到的位置，只重算受影响规则。文件仍在回放或暂停时不提前分析未播放报文；文件分析完成后覆盖整份文件。扫描期间原结果标为待更新，完成后一次替换。正常报文列表、图表、统计、PCAP 保存和会话计数均不重置。
- 多次修改取消旧版本结果发布；切换会话也取消旧发布。关闭规则立即移除其结果。扫描时文件大小/修改时间变化、文件丢失或读取失败，会提示失败并保留原结果；修复文件后可重新应用规则，文件被替换则应重新打开。
- “暂停预警”冻结检测结果，采集或文件读取继续；恢复时重评当前实时窗口或文件已处理部分，暂停期间的数据可参与恢复后的重评。
- 告警 CSV 可导出当前结果及触发参数。规则变更写入运行事件日志；告警出现、恢复和撤下的可观察变化也写入同一日志。日志按秒观察，不能作为逐包完整审计。
- “查看相关报文”复用工作台现有目标 IP、端口和协议筛选，展示的是相关候选报文，不等同该规则窗口的完整证据集。较旧报文已离开列表时，通过原 PCAP 复查。

## 资源边界与局限

每条规则至多 100000 个窗口事件、4096 个活动对象和 1000 条合并告警；ARP 基线至多 4096 项。触及容量时显示检测可能不完整，不将缺失流量视为正常。数量阈值上限 100000，端口扫描上限 65536，与端口范围和窗口存储能力一致。

时间戳回退的报文在相应规则中跳过并计数，页面显示次数；不静默重新排序整个文件。SYN 是包频率规则，不验证握手完成、攻击意图或服务端资源耗尽；UDP 高频也可能是正常业务。ARP 映射变化可能来自设备更换和正常切换；不同 VLAN 未建立独立的映射域，跨 VLAN 抓包需谨慎解释。普通主机不能默认看到整个交换网络。

本阶段不实现防火墙封禁、TCP 流重组、攻击归因。长时间运行和高负载性能需要另外验收，本功能的短时回归不能替代全天测试。

## 构建与自动验证

源码由 CMake 组织，MSVC 编译、链接生成主程序及测试程序；CTest 负责逐项运行。先正常关闭正在运行的旧 FlowGuard，否则 Windows 不允许链接器覆盖该 exe。

在已按 README 配置好的 Developer PowerShell 中：

```powershell
cmake --preset windows-msvc
cmake --build --preset windows-msvc
ctest --test-dir build/windows-msvc --output-on-failure --no-tests=error
```

按 README 使用本机 Qt/Npcap 的 Windows 目录设置运行依赖；PATH 中使用正常的 Windows 反斜杠路径。不能把程序未启动、缺 DLL 或测试超时算作通过。

新增 `alert_detection` 覆盖规则边界、请求/应答、端口去重、映射变化、动态配置、文件重算、统计隔离、倍速一致、文件变化和会话隔离。`alert_gui_integration` 验证五条规则展示、动态阈值增删告警、开关规则和跳转工作台；使用实际 MainWindow，并输出页面渲染图到本机 build 目录。完整现有回归也必须通过。

## 用户亲自验收

样本由 `tests/generate_alert_samples.py` 生成，只有离线构造，不发送网络报文。

1. 构建完成后按 README 启动 `build/windows-msvc/FlowGuard.exe`，点击侧边“预警监测”。等待输入时应显示等待状态。
2. 打开 `tests/data/alerts-demo.pcap`，使用默认规则。共 2082 包，预期出现五类合并告警：SYN 峰值 600、扫描 30 个不同端口、回声请求 350、UDP 1100、ARP 变化 1 次。前四项随文件后续时间推进显示恢复，ARP 显示输入结束时仍异常。
3. 展开规则设置，把 SYN 阈值从 500 改为 1000，点击应用。后台重新检测后 SYN 告警撤下，其余四条保留。再改成 100，SYN 告警重新出现。核对统计分析页仍为原包数。
4. 关闭 UDP 规则并应用，其告警撤下；重新启用后自动重算并恢复。选择记录检查窗口、阈值、峰值、时间、关联序号和 ARP MAC 变化。
5. 尝试标记确认、查看相关报文、导出 CSV。切换页面不停止检测，显示筛选不改变预警统计。
6. 打开 `tests/data/alerts-normal.pcap`，共 52 包，恢复默认阈值后预期无告警，上一文件结果不能混入。
7. 可再按捕获时间回放异常文件，验证暂停/继续与不同倍速的结果；实时采集用实际正常流量调低阈值观察规则命中，不需要对外发起攻击流量。

本阶段完成后停在功能分支供人工验收，不自动提交、推送或合并 main。

- 后台预警检查已扩展到 80 项并通过；Qt 预警页面测试也通过，包括连续应用设置、输入结束后恢复预警，以及五类告警峰值精确核对。首次实现另用 Windows 原生平台和字体渲染，确认中文、规则区、五条告警和详情可读。
- 构建日志：本机 `build/alert-final-build.log`；完整回归：`build/alert-ctest-final.log`；页面渲染：`build/windows-msvc/alert-monitor.png`、`alert-settings.png`。
- 修正本机生成的 MSVC 头文件依赖前缀乱码，并清理重建所有目标，验证 Ninja 正确记录 `packet_types.h` 依赖；没有把本机工具路径或缓存写入共享配置。

## 实现后逻辑复核

复核时发现并修复以下边界问题，均补充回归检查：

1. 实时空闲计时器推进后，仍在窗口内、按捕获顺序到达的延迟报文曾被当作乱序。现将“最后收到的报文时间”与“当前评估时刻”分开；窗口外的过期报文也不会重新激活告警。
2. 已恢复告警的新报文未达到阈值时，详情的当前数量曾少算新加入的一包。现在每次有效计数更新详情，触发时间只在命中规则时更新。
3. 暂停预警期间没有流量，恢复时曾短暂重现过期告警。现在后台时钟与缓存仍正常推进，显示结果保持冻结，恢复后按当前窗口重评。
4. 文件在暂停预警期间结束，原按钮会被禁用，无法恢复。现在仍可恢复，并自动分析完整的已处理文件内容。
5. 连续点击应用规则，后一次可能被主工具栏的忙碌保护忽略。现在每份已应用配置进入同一控制线程队列，后台按版本取消过时重算，以最新设置发布结果。

已检查处理线程、预警锁、文件重算线程与 Qt 控制线程的调用关系；预警模块不反向获取处理线程锁。新会话与新规则版本都会阻止旧扫描发布。新增慢速回放测试验证重新检测只读取已播放的前缀，不偷跑后续报文；容量边界测试验证事件、对象、告警数量上限及提示。

图表与 StatisticsEngine 未改动。PCAP 重算使用独立 Reader，测试核对主会话累计包数、累计字节数、未修改规则的告警证据保持不变。完整回归覆盖原有读写、采集和 GUI；不能据此保证任意负载下绝无问题。

样本已修正为方向、序号及确认号相互对应的 TCP 握手、ICMP 回应及一致的 ARP 发送地址。独立核对结果：

| 文件 | 包数 | 报文组成 | 默认检测结果 |
| --- | --- | --- | --- |
| alerts-normal.pcap | 52 | TCP 30、ICMP 20、ARP 2 | 无告警 |
| alerts-demo.pcap | 2082 | TCP 630、ICMP 350、UDP 1100、ARP 2 | 五类告警；峰值 600 / 30 / 350 / 1100 / 1 |

两份文件时间戳有序、报文长度正确，IPv4/TCP/UDP/ICMP 校验和检查通过；正常文件的十组三次握手和回声请求/应答方向逐组核对。文件均为离线构造，不是个人抓包。
